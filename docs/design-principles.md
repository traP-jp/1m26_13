# stoQの設計原則

## プロダクトの核

stoQは、traPの講習会を「その場限りのイベント」にせず、これから受ける人、後から学ぶ人、次年度に引き継ぐ人が同じ情報を使えるようにするサービスである。

講習会の情報を集めること自体が目的ではない。受講者が学び始めやすくなり、運営者が迷わず準備でき、翌年の担当者が過去の知見を再利用できることを優先する。

## UXで大切にすること

### 1. 三つの利用場面を一つの情報で支える

一つの講習会ページには、次の三者に必要な情報を過不足なくまとめる。

- これから行われる講習会に参加する人
- 過去の資料や動画から後追いで受講する人
- 次年度に同じ講習会を担当する人

開催前後で別のページ構成に切り替えず、いつ見ても同じ項目・同じ順序で表示する。時期によって変えるのは情報の有無や状態だけにする。

### 2. 入力することが、そのまま準備になる

作成画面は別のTODOリストを管理させない。講習会名、開催枠、場所、資料、告知などを順に埋めることで、自然に開催準備が整う構成にする。

外部サービスを自動操作できない場合も、必要な情報と次の行動を示し、knoQ本文や告知文などをコピーできる形にする。自動化できないことを、運営者の記憶や経験だけに委ねない。

### 3. 全体像と現在地を同時に見せる

Stepは作業全体を示す横方向のナビゲーション、各Step内の項目は現在の入力箇所へ移動する縦方向のナビゲーションとして扱う。入力済みかどうかも同じ場所で確認できるようにする。狭い幅ではStep名を省略せず、二行にして読める状態を保つ。

Stepを切り替えてもナビゲーションを見失わせず、クリックによって予想外にスクロール位置を変えない。利用者が「今どこにいて、次に何が残っているか」を常に把握できることを優先する。

### 4. 入力負荷をシステム都合で増やさない

必須項目は最小限にし、未確定のままでも保存・公開できる。開催枠の追加時に「第1回」の次を「第2回」と補うなど、安全に推測できる定型入力は支援する。

データモデル上は必要でも、利用者に判断する価値がない設定を入力させない。特に受講完了条件のような複雑さは、まず講習会単位の明示的な完了操作で扱う。

### 5. 過去の講習会を再利用しやすくする

年度ごとの講習会は別の記録として保持しながら、対応する過年度の講習会をたどれるようにする。検索では複数年度がある場合に最新年度を基本表示とし、必要な人だけ過年度を展開できるようにする。

新しい講習会は白紙からだけでなく、過去の講習会を引き継いで作れるようにする。内容や構成は再利用し、日程や講師など年度ごとに変わる情報は改めて設定する。

### 6. 講習会と開催枠を混同しない

「2026年度 Git講習会」のような学びのまとまりを講習会、「第1回」「Web編」「同じ内容の別日程」のような実施単位を開催枠として扱う。日付、時刻、講師、形式、場所は開催枠に属し、資料は講習会全体と開催枠ごとの両方に設定できるようにする。

この区別はシステム都合ではなく、受講者が「何を学ぶか」と「いつ参加するか」を別々に理解するために使う。

### 7. 分からないことを、ないことにしない

「調査では未確認」と「確認したが該当なし」を区別する。日付から開催済みと推測したり、似た名前だけで正式な継承関係を確定したりしない。

過去データには情報源を残し、推測によるつながりはその判定方法を表示する。情報の量よりも、利用者がどこまで信用できるかを判断できることを優先する。

### 8. 外部サービスへの書き込みは利用者が決める

traQ、knoQ、Wikiなどから取得できる情報は読み取りに使う。一方、告知や登録は内容を確認してから利用者自身が行う。自動投稿や自動完了は、明確に求められない限り行わない。

バッジも講習会ページから本人が受講完了を記録して獲得する。他者への公開は初期状態で非公開とし、共有する範囲と対象は本人が選ぶ。

## UIで大切にすること

### 1. traQの延長として感じられること

basiQ UIの部品と振る舞いを優先し、M PLUS 1pを使う。traQで見慣れた密度、色、アイコン、サイドバーの構成に寄せ、独自部品や独自CSSは必要な場合だけ追加する。

### 2. コンパクトで、文章を読むように走査できること

大きなカードや装飾的な余白で情報を分断しない。プレーンテキストに近い密度を保ち、見出し、ラベル、値の階層だけで素早く読めるようにする。

資料や情報源が多い場合は最初からすべてを広げず、件数と代表的な内容を示して残りを展開できるようにする。情報を削るのではなく、必要な順番で見せる。

### 3. 見た目のルールを局所的に変えない

文字サイズ、アイコンサイズ、角丸、線の太さ、余白の単位を画面間で統一する。意味のない影、左側だけの強調線、過剰な囲み、装飾のためだけの文言は使わない。

番号は情報階層を助ける範囲で使い、内容より強く見せない。状態や選択を示す色にも一貫した意味を持たせる。

### 4. ラベルだけで入力内容が分かること

運営者が「ここに何を書くのか」を迷わない具体的なラベルと、必要な場合だけ短い質問文・例を置く。同じ意味の補足を重ねたり、指示されていない説明文を足したりしない。

候補選択ではtraQ ID、表示名、グループ名、講習会名の表記揺れや入力途中にも耐える検索にする。Enterで先頭候補を選べるなど、繰り返し入力を妨げない。

## 迷ったときの判断基準

新しい項目や表現を追加する前に、次の順で判断する。

1. 三つの利用場面のうち、誰のどの行動に必要か。
2. 既存の情報から安全に導けないか。
3. 入力者に判断させるだけの価値があるか。
4. basiQ UIの既存部品とtraQの慣習で表現できないか。
5. 未確認情報を確定情報のように見せていないか。
6. 画面を見た人が説明なしで次の行動を選べるか。
